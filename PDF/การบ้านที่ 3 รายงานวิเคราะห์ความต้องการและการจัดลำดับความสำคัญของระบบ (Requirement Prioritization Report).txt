1. เกณฑ์และสูตรคำนวณที่ใช้ในการวิเคราะห์ (Methodology) 
การจัดลำดับความสำคัญของฟังก์ชัน (Requirement Prioritization) 
จะอิงจากสัดส่วนผลกระทบของผู้ใช้งานจริงผ่านเกณฑ์ Problem-Centric Personas 
เพื่อให้การพัฒนาซอฟต์แวร์ตอบโจทย์ความจำเป็นเร่งด่วนที่สุดของผู้ใช้ โดยมีสูตรคำนวณสัดส่วนดังนี้: 
 
เปอร์เซ็นต์กลุ่มปัญหา (%) = ( จำนวนผู้ใช้ที่ตรงตามเกณฑ์ Test Case / จำนวนผู้ตอบแบบสอบถามทั้งหมด (20 
คน) ) * 100 
 
เกณฑ์การคัดกรองตาม Test Cases (Mapping Rules) 
• [IL] Information Lost Group (90%): คัดจากผู้ตอบแบบสอบถามในข้อ 3.2 
(พบปัญหาแชทรันหายในความถี่ระดับ 2) และในข้อ 3.3 ระบุว่าได้รับผลกระทบเชิงลบต่อการเรียนจริง 
(เช่น หาไฟล์ไม่เจอ, ทำงานล่าช้า, หรือได้ข้อมูลเก่าจนส่งงานผิดพลาด) 
• [SA] Social Anxiety Group (85%): คัดจากผู้ตอบแบบสอบถามในข้อ 2.2 
(มีความถี่ในการเลือกที่จะไม่ถามคำถามในห้องเรียนระดับ 2) ร่วมกับข้อ 3.1 
ที่ระบุว่าสาเหตุหลักมาจากปัจจัยด้านจิตวิทยาความกังวล (เช่น กลัวคำถามง่ายเกินไป, 
ไม่อยากเป็นจุดสนใจ หรือเกรงใจไม่อยากให้แจ้งเตือนรบกวนผู้อื่น) 
• [UR] Unverified Reliability Group (80%): คัดจากผู้ตอบแบบสอบถามในข้อ 4.3 
ที่ให้คะแนนความคาดหวังและความต้องการต่อระบบตรวจสอบความถูกต้องของคำตอบ (Verified 
Answer) ในระดับสูงมาก (ระดับคะแนน 4 และ 5)

3. การจัดลำดับความต้องการระบบตามลำดับก่อน-หลัง (Prioritization Roadmap) 
จากการแปลผลสถิติความต้องการและขนาดของกลุ่มปัญหาของผู้ใช้งาน (Data-Driven Prioritization) 
แผนงานการพัฒนาซอฟต์แวร์ถูกแบ่งออกเป็น 3 เฟส ดังต่อไปนี้: 
 
🚀 เฟสที่ 1: แกนหลักของระบบ (Must Have - High Priority) ทำก่อนทันที 
เป็นกลุ่มฟังก์ชันที่แก้ไขปัญหาขั้นรุนแรงที่กระทบต่อนักศึกษาเกินกว่า 85% ในชีวิตประจำวัน 
ลำดับ 1: ระบบจัดหมวดหมู่คำถามตามรายวิชา/หัวข้อ (แก้ปัญหา [IL] - 90%) 
• ความสำคัญ: สูงสุดอันดับ 1 (เนื่องจากมีสัดส่วนผู้เจอปัญหาสูงที่สุดถึง 18/20 คน) 
• ฟังก์ชันย่อยที่ต้องพัฒนา (Features): 
o Subject-based Threads: โครงสร้างฟอรัมแยกตามรหัสวิชาหลักและวิชาเลือก 
เพื่อยุติปัญหาข้อความสับสนปนเปกัน 
o Pinned Academic Repository: คลังจัดเก็บไฟล์ประกาศ ข้อมูลการสอบ 
และโจทย์การบ้านแบบถาวร โดยระบบจะไม่ลบไฟล์ทิ้งตามเงื่อนไขเวลาเหมือนแชทไลน์ 
(แก้ไขปัญหา "ไฟล์หมดอายุ" และปัญหาการส่งงานล่าช้า) 
o Keyword Search: ระบบสืบค้นกระทู้ด้วยคำสำคัญเพื่อลดการถามคำถามซ้ำ 
ลำดับ 2: ระบบถามคำถามแบบไม่ระบุตัวตน (แก้ปัญหา [SA] - 85%) 
• ความสำคัญ: สูงสุดอันดับ 2 (แก้ไขกำแพงจิตวิทยาของนักศึกษาจำนวน 17/20 คน) 
• ฟังก์ชันย่อยที่ต้องพัฒนา (Features): 
o Post As Anonymous: 
ฟังก์ชันสลับโหมดการตั้งกระทู้หรือตอบคำถามโดยไม่แสดงชื่อและอีเมลจริงต่อบุคคลทั่วไป 
ช่วยแก้ปัญหาความกลัวสายตาคนอื่นในกรณีที่คำถามง่ายเกินไป 
o Asynchronous Board: เปลี่ยนรูปแบบจากการแชทสดมาเป็นกระทู้ถาม-ตอบทิ้งไว้ 
เพื่อลดแรงกดดันเรื่องการส่งเสียงแจ้งเตือนไปรบกวนผู้อื่นในช่วงกลางดึกหรือวันหยุด

🛠️ เฟสที่ 2: เพิ่มประสิทธิภาพและขยายส่วนควบคุม (Should Have - Medium Priority) ทำลำดับถัดมา 
กลุ่มฟังก์ชันเพื่อเพิ่มความน่าเชื่อถือทางวิชาการและรองรับพฤติกรรมการสื่อสารเชิงเทคนิค 
ลำดับ 3: ระบบรับรองความถูกต้องของคำตอบ (แก้ปัญหา [UR] - 80%) 
• ความสำคัญ: อันดับ 3 (ตอบสนองความต้องการความแม่นยำของข้อมูลจำนวน 16/20 คน) 
• ฟังก์ชันย่อยที่ต้องพัฒนา (Features): 
o Role-based Authorization: ระบบแยกประเภทบัญชีผู้ใช้ระหว่าง นักศึกษา (Student), 
ผู้ช่วยสอน (TA), และอาจารย์ผู้สอน (Instructor) 
o Verified Answer Badge: ตราสัญลักษณ์รับรองความถูกต้องทางวิชาการ 
โดยสิทธิ์การกดรับรองจะมีเฉพาะกลุ่มอาจารย์หรือ TA เท่านั้น 
เพื่อให้นักศึกษามีกลไกข้อมูลที่เชื่อถือได้ทันที (Single Source of Truth) 
ลำดับ 4: ระบบกล่องข้อความสำหรับเขียนโค้ดและแนบสื่อคอมพิวเตอร์ (แก้ปัญหา [FC] - 75%) 
• ความสำคัญ: อันดับ 4 (ตอบโจทย์พฤติกรรมของนักศึกษาฝั่ง Coder จำนวน 15/20 คน) 
• ฟังก์ชันย่อยที่ต้องพัฒนา (Features): 
o Rich Text Editor: ตัวจัดการเนื้อหาในหน้าตั้งกระทู้ 
o Code Snippet Block: กล่องแสดงซอร์สโค้ดเฉพาะทางที่รองรับการทำ Syntax Highlighting 
แยกสีตามไวยากรณ์ภาษา (เช่น Python, JavaScript, C# 
ตามที่กลุ่มผู้เรียนระบุในทักษะทางเทคนิค) 
o Screenshot Uploader: ระบบอัปโหลดและบีบอัดไฟล์รูปภาพหน้าจอสำหรับภาพ Error 
 
⏱️ เฟสที่ 3: ระบบส่วนขยายในอนาคต (Nice to Have - Low Priority) ทำหลังสุด 
ฟังก์ชันเพิ่มเติมที่คัดกรองจากความเห็นปลายเปิดและข้อเสนอแนะเพิ่มเติมของผู้ใช้งาน

siriluk.pus)

o Advanced Filtering System: ค้นหากรองกระทู้แยกตามช่วงเวลาวิกฤต เช่น กรองเฉพาะ

4. ผลลัพธ์การตรวจสอบความต้องการ (Validation Result) 
เพื่อป้องกันความผิดพลาดในการกำหนดความต้องการ (Requirement Errors) 
คณะผู้จัดทำได้นำโครงสร้างระบบนี้ไปทำการทวนสอบกับกลุ่มตัวอย่างเป้าหมาย (User Validation) 
เพื่อยืนยันความถูกต้อง: 
1. กลุ่มปัญหา [IL] และ [FC]: คุณ tanitsin.don และคุณ tanaphat.jar ยืนยันว่า 
แพลตฟอร์มที่แยกรายวิชาและมีกล่องครอบโค้ดจะช่วยลดเวลาในการดีบั๊กงานช่วงดึกได้จริงมากกว่าระบ
บแชทเดิม 
2. กลุ่มปัญหา [SA]: คุณ siriluk.pus ยืนยันว่า ฟีเจอร์ Anonymous 
ช่วยให้กล้ากดส่งคำถามพื้นฐานโดยไม่มีความกังวลใจเรื่องสายตาของคนอื่นในหลักสูตร 
 
หมายเหตุ: ข้อมูลสถิติและโครงสร้างทั้งหมดในรายงานฉบับนี้ ได้รับการตรวจสอบและปรับปรุงความสอดคล้อง
